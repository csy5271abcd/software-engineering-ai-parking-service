# PROJECT_RULES.md

# SmartPark 프로젝트 작업 규칙 문서

## 1. 문서 개요

### 1.1 문서 목적

본 문서는 SmartPark 프로젝트의 코드 작성 규칙, 폴더 관리 규칙, 문서 작성 규칙, commit/tag/CHANGELOG 관리 규칙을 정의하기 위해 작성되었다.

SmartPark는 React Native 기반 모바일 앱, Spring Boot 기반 백엔드, MySQL 데이터베이스, Naver Maps API, NFC 기반 이용 흐름, AI 또는 규칙 기반 혼잡도 분석을 활용하는 AI 기반 주차난 해결 서비스이다.

본 문서는 Claude Code, Codex 등 AI 개발 도구가 SmartPark 프로젝트를 일관성 있게 이해하고 작업할 수 있도록 제공하는 하네스 문서이다. AI 도구가 임의로 구조를 변경하거나, 문서와 코드 간 연결성을 해치지 않도록 프로젝트 작업 기준을 명확히 정리한다.

---

### 1.2 문서 적용 범위

본 문서는 다음 작업에 적용한다.

| 구분      | 적용 대상                                                |
| --------- | -------------------------------------------------------- |
| 코드 작성 | React Native 프론트엔드, Spring Boot 백엔드, 테스트 코드 |
| 폴더 관리 | `docs/`, `src/`, `frontend/`, `backend/` 하위 구조       |
| 문서 작성 | 요구사항, 설계, 제품 기획, 하네스, 테스트 문서           |
| 형상관리  | Git commit, tag, CHANGELOG, 브랜치 관리                  |
| AI 작업   | Claude Code, Codex에 전달하는 프롬프트와 결과 검토       |
| 품질관리  | 구현 전후 체크리스트, 문서-코드 연결성 점검              |

## 2. 프로젝트 기본 원칙

### 2.1 핵심 원칙

| 원칙               | 설명                                                                      |
| ------------------ | ------------------------------------------------------------------------- |
| 문서 우선          | 기능 구현 전 관련 문서의 범위와 요구사항을 먼저 확인한다.                 |
| 구조 유지          | 기존 폴더 구조와 네이밍 규칙을 임의로 변경하지 않는다.                    |
| 화면-기능-API 연결 | 화면 구조, 기능 명세, API 후보가 서로 연결되도록 작성한다.                |
| 작은 단위 작업     | 한 번에 큰 범위를 수정하지 않고 기능, 화면, 문서 단위로 나누어 작업한다.  |
| 변경 이력 기록     | 주요 변경은 commit 메시지와 CHANGELOG에 기록한다.                         |
| AI 결과 검토       | Claude Code와 Codex 결과물은 그대로 반영하지 않고 문서 기준으로 검토한다. |

---

### 2.2 작업 순서 원칙

SmartPark 작업은 다음 순서를 기본으로 한다.

```text
문서 확인
→ 작업 범위 정의
→ 파일 위치 확인
→ 코드 또는 문서 작성
→ 자체 검토
→ CHANGELOG 반영
→ commit
→ tag 생성
→ push
```

## 3. 저장소 폴더 관리 규칙

### 3.1 전체 폴더 구조 기준

SmartPark 저장소는 다음 구조를 기준으로 관리한다.

```text
software-engineering-ai-parking-service/
├── README.md
├── CHANGELOG.md
├── FOLDER_STRUCTURE.md
├── configuration_management_plan.md
├── docs/
│   ├── requirements/
│   ├── plan/
│   ├── design/
│   ├── product/
│   ├── harness/
│   └── test/
└── src/
    ├── frontend/
    └── backend/
```

---

### 3.2 루트 디렉터리 규칙

| 파일                               | 관리 규칙                                                       |
| ---------------------------------- | --------------------------------------------------------------- |
| `README.md`                        | 프로젝트 개요, 기술 스택, 산출물 현황, 저장소 구조를 설명한다.  |
| `CHANGELOG.md`                     | 버전 tag별 변경 사항을 누적 기록한다.                           |
| `FOLDER_STRUCTURE.md`              | 폴더와 파일의 역할을 설명한다. 폴더 구조 변경 시 함께 수정한다. |
| `configuration_management_plan.md` | 형상관리 기준 문서로 유지한다.                                  |
| `docs/`                            | 모든 문서 산출물을 저장한다.                                    |
| `src/`                             | 실제 구현 코드를 저장한다.                                      |

루트 디렉터리에는 임시 파일, 개인 메모, 테스트용 파일을 두지 않는다. 임시 파일이 필요한 경우 작업 후 삭제하거나 적절한 폴더로 이동한다.

---

### 3.3 docs 폴더 규칙

| 폴더                 | 역할                                              | 작성 규칙                                   |
| -------------------- | ------------------------------------------------- | ------------------------------------------- |
| `docs/requirements/` | 프로젝트 정의서, 요구사항 정의서, 요구사항 분석서 | 공식 과제 산출물 중심으로 관리              |
| `docs/plan/`         | 프로젝트 관리 계획, 일정, WBS                     | 일정과 관리 기준 중심으로 작성              |
| `docs/design/`       | 시스템 설계, 화면 흐름, UI/UX 설계                | 요구사항을 구현 구조로 변환                 |
| `docs/product/`      | 페르소나, 사용자 여정, 경쟁 분석, 비즈니스 모델   | 요구사항과 UI/UX 설계의 근거로 작성         |
| `docs/harness/`      | AI 개발 도구용 기준 문서                          | Claude Code와 Codex가 참고할 작업 기준 작성 |
| `docs/test/`         | 인스팩션, 테스트 결과, 결함 기록                  | 요구사항 검증과 품질관리 중심으로 작성      |

---

### 3.4 docs/harness 폴더 규칙

`docs/harness/`는 AI 개발 도구가 SmartPark 프로젝트를 일관성 있게 이해하도록 돕는 기준 문서 공간이다.

| 문서                  | 역할                                 |
| --------------------- | ------------------------------------ |
| `PRD.md`              | 제품 요구사항 기준 문서              |
| `FEATURE_SPEC.md`     | 기능별 상세 명세 문서                |
| `SCREEN_STRUCTURE.md` | 화면 구조와 네비게이션 기준 문서     |
| `PROJECT_RULES.md`    | 프로젝트 작업 규칙 문서              |
| `CLAUDE.md`           | Claude Code 프론트엔드 구현 지침     |
| `CODEX.md`            | Codex 백엔드/문서화 작업 지침        |
| `PROMPT_LOG.md`       | 프롬프트와 결과, 수정 사항 기록 문서 |

하네스 문서를 수정할 때는 다음 원칙을 따른다.

1. 기존 문서와 충돌하는 규칙을 만들지 않는다.
2. 화면, 기능, API, 폴더 구조가 서로 연결되도록 작성한다.
3. Claude Code와 Codex가 바로 이해할 수 있도록 명령형 기준을 명확히 작성한다.
4. 변경된 규칙은 `CHANGELOG.md`에 반영한다.
5. 작업 완료 시 버전 tag를 생성한다.

## 4. 문서 작성 규칙

### 4.1 기본 형식

모든 문서는 Markdown 형식으로 작성한다.

| 항목        | 규칙                                           |
| ----------- | ---------------------------------------------- |
| 파일 확장자 | `.md` 사용                                     |
| 제목        | 문서 최상단에 파일명 또는 문서명을 명확히 작성 |
| 섹션 구조   | `##`, `###` heading을 사용하여 계층 구조 유지  |
| 표 사용     | 기능, 화면, 요구사항, 상태값은 표로 정리       |
| 코드 블록   | 명령어, 폴더 구조, 흐름은 코드 블록으로 작성   |
| 문체        | 보고서형 문체 사용                             |
| 이모지      | 공식 문서와 하네스 문서에서는 사용하지 않음    |

---

### 4.2 문서 내용 작성 기준

문서는 다음 기준을 충족해야 한다.

| 기준        | 설명                                                          |
| ----------- | ------------------------------------------------------------- |
| 목적 명확성 | 문서의 작성 목적과 활용 범위를 먼저 설명한다.                 |
| 연결성      | 관련 문서와 어떤 관계가 있는지 표시한다.                      |
| 추적성      | 요구사항, 화면, 기능, 테스트가 연결되도록 작성한다.           |
| 실무성      | 실제 구현에 사용할 수 있는 수준으로 구체화한다.               |
| 유지보수성  | 이후 변경 시 어떤 부분을 수정해야 하는지 알 수 있게 작성한다. |

---

### 4.4 문서 수정 규칙

문서를 수정할 때는 다음 절차를 따른다.

```text
수정 대상 문서 확인
→ 관련 문서 영향 범위 확인
→ 내용 수정
→ 오타 및 표 정렬 확인
→ CHANGELOG 갱신
→ commit
→ 필요한 경우 tag 생성
```

예를 들어 `SCREEN_STRUCTURE.md`에서 화면명이 변경되면 `FEATURE_SPEC.md`, `CLAUDE.md`, `CODEX.md`, `README.md`의 관련 항목도 함께 확인한다.

## 5. 코드 작성 공통 규칙

### 5.1 공통 원칙

| 원칙               | 설명                                                        |
| ------------------ | ----------------------------------------------------------- |
| 단일 책임          | 하나의 파일과 함수는 하나의 명확한 책임을 가진다.           |
| 명확한 네이밍      | 역할이 드러나는 이름을 사용한다.                            |
| 과도한 추상화 금지 | 초기 MVP 단계에서는 불필요하게 복잡한 구조를 만들지 않는다. |
| 하드코딩 최소화    | 반복 사용되는 값은 상수 또는 설정 파일로 분리한다.          |
| 예외 처리 포함     | API 실패, 권한 거부, 빈 데이터 상태를 고려한다.             |
| 주석 활용          | 복잡한 로직에는 짧고 명확한 주석을 작성한다.                |

---

### 5.2 네이밍 공통 규칙

| 대상            | 규칙                         | 예시                             |
| --------------- | ---------------------------- | -------------------------------- |
| 폴더            | 소문자 또는 도메인 기준      | `parking`, `provider`, `payment` |
| React 컴포넌트  | PascalCase                   | `ParkingCard`                    |
| React 화면      | PascalCase + Screen          | `HomeMapScreen`                  |

| Java 클래스     | PascalCase                   | `ParkingLotService`              |
| Java 메서드     | camelCase                    | `findNearbyParkingLots`          |
| DB 테이블       | snake_case                   | `parking_lots`                   |
| API 경로        | kebab-case 또는 RESTful path | `/api/parking-lots`              |

## 6. React Native 프론트엔드 규칙

### 6.1 기본 구조

프론트엔드는 다음 구조를 기준으로 작성한다.

```text
src/frontend/
└── src/
    ├── navigation/
    ├── screens/
    ├── components/
    ├── services/
    ├── types/
    ├── hooks/
    ├── constants/
    └── data/
```

---

### 6.2 화면 작성 규칙

| 규칙                               | 설명                                             |
| ---------------------------------- | ------------------------------------------------ |
| 화면 파일은 `screens/` 하위에 작성 | 화면 목적에 맞는 도메인 폴더에 배치              |
| 화면명은 `Screen` 접미사 사용      | `ParkingDetailScreen.tsx`                        |
| 화면 내부 API 직접 호출 지양       | API 호출은 `services/` 또는 custom hook으로 분리 |
| 로딩/오류/빈 상태 포함             | 사용자가 상태를 이해할 수 있도록 UI 제공         |
| 네비게이션 이름 통일               | `constants/routes.ts`에 route 이름을 정의        |

---

### 6.3 컴포넌트 작성 규칙

| 규칙                                          | 설명                                                 |
| --------------------------------------------- | ---------------------------------------------------- |
| 재사용 컴포넌트는 `components/common/`에 배치 | 버튼, 입력창, 헤더, 모달 등                          |
| 도메인 컴포넌트는 도메인 폴더에 배치          | `components/parking/ParkingCard.tsx`                 |
| 컴포넌트 props 타입 명시                      | TypeScript interface 사용                            |
| 스타일 분리                                   | 한 파일 안에서 스타일을 명확히 분리하거나 theme 사용 |
| 상태값은 enum 또는 상수 사용                  | 문자열 직접 비교 최소화                              |

---

### 6.4 프론트엔드 상태값 규칙

## 7. Spring Boot 백엔드 규칙

### 7.1 기본 구조

백엔드는 다음 구조를 기준으로 작성한다.

```text
src/backend/
└── src/main/java/com/smartpark/
    ├── domain/
    ├── controller/
    ├── service/
    ├── repository/
    ├── dto/
    ├── config/
    └── common/
```

---

### 7.2 계층별 역할

| 계층         | 역할                           |
| ------------ | ------------------------------ |
| `controller` | HTTP 요청과 응답 처리          |
| `service`    | 비즈니스 로직 처리             |
| `repository` | 데이터베이스 접근              |
| `domain`     | Entity, enum, 도메인 모델 관리 |
| `dto`        | 요청/응답 데이터 객체 관리     |
| `config`     | 보안, CORS, 외부 API 설정      |
| `common`     | 공통 응답, 예외, 유틸리티 관리 |

---

### 7.3 백엔드 작성 원칙

| 규칙                            | 설명                                   |
| ------------------------------- | -------------------------------------- |
| Controller는 얇게 유지          | 요청 검증 후 Service 호출 중심         |
| Service에 비즈니스 로직 작성    | 요금 계산, 상태 변경, 승인 처리 등     |
| Repository는 데이터 접근만 담당 | 복잡한 정책 로직 작성 금지             |
| DTO와 Entity 분리               | API 응답에 Entity를 직접 노출하지 않음 |
| enum 사용                       | 상태값은 문자열이 아니라 enum으로 관리 |
| 예외 응답 통일                  | 공통 오류 응답 형식 사용               |

---

## 11. Git commit 규칙

### 11.1 Commit 메시지 형식

Commit 메시지는 다음 형식을 사용한다.

```text
[구분자-번호] 변경 내용
```

예시:

```text
[DOCS-15] SmartPark 화면 구조 문서 추가
[DOCS-16] 프로젝트 작업 규칙 문서 추가
[FEAT-01] 현재 위치 기반 주차장 조회 화면 구현
[FIX-01] 주차장 상세 화면 상태 표시 오류 수정
[TEST-01] NFC 이용 시작 테스트 케이스 추가
```

---

### 11.2 Commit 구분자

| 구분자     | 의미                            |
| ---------- | ------------------------------- |
| `DOCS`     | 문서 추가 또는 수정             |
| `FEAT`     | 기능 추가                       |
| `FIX`      | 오류 수정                       |
| `TEST`     | 테스트 추가 또는 수정           |
| `REFACTOR` | 코드 구조 개선                  |
| `CHORE`    | 설정, 빌드, 의존성 등 기타 작업 |

### 11.3 Commit 작성 원칙

| 원칙                       | 설명                                                    |
| -------------------------- | ------------------------------------------------------- |
| 변경 단위 분리             | 서로 다른 목적의 변경을 하나의 commit에 섞지 않는다.    |
| 구체적 메시지 작성         | 무엇을 추가/수정했는지 알 수 있게 작성한다.             |

| 대규모 변경 전 확인        | 폴더 구조나 API 구조 변경 전 관련 문서를 먼저 확인한다. |

## 12. Tag 규칙

### 12.1 버전 형식

버전 tag는 다음 형식을 사용한다.

```text
vMajor.Minor.Patch
```

예시:

```text
v0.3.0
v0.3.1
v0.3.2
v0.3.3
```

---

### 12.2 버전 의미

| 구분  | 의미                                             |
| ----- | ------------------------------------------------ |
| Major | 요구사항 변경 또는 프로젝트 범위의 큰 변경       |
| Minor | 주요 문서 추가, 기능 단위 추가, 과제 산출물 추가 |
| Patch | 오타 수정, 문구 보완, CHANGELOG 갱신             |

---

### 12.3 Tag 생성 기준

Tag는 다음 경우에 생성한다.

1. 공식 과제 산출물을 추가했을 때
2. 주요 하네스 문서를 추가했을 때
3. 제품 기획 문서 묶음을 완료했을 때
4. 설계 문서 또는 테스트 문서를 완료했을 때
5. README, CHANGELOG 등 저장소 기준 문서가 큰 단위로 갱신되었을 때

---

### 12.4 Tag 명령어 예시

```bash
git tag -a v0.3.3 -m "SmartPark 프로젝트 작업 규칙 문서 추가"
git push origin main --tags
```

| API 경로가 REST 원칙에 맞는가                       |      |
| Controller, Service, Repository 역할이 분리되었는가 |      |
| Entity와 DTO가 분리되었는가                         |      |
| 상태값이 enum으로 관리되는가                        |      |
| 결제, NFC, 신고 등 예외 흐름이 고려되었는가         |      |
| 화면에서 필요한 응답값을 제공하는가                 |      |

---

## 17. 금지 사항

SmartPark 프로젝트에서 다음 작업은 사전 확인 없이 수행하지 않는다.

1. 기존 폴더 구조 전체 변경
2. 문서 파일명 임의 변경
3. 화면명 또는 route 이름 임의 변경
4. 상태값 enum 임의 변경
5. API 경로 체계 임의 변경
6. README와 CHANGELOG 없이 주요 문서 추가
7. 기존 문서와 충돌하는 새로운 규칙 추가
8. AI 도구 결과물을 검토 없이 그대로 반영
9. 임시 파일을 루트 디렉터리에 방치
10. 개인정보, API Key, 결제 Key를 저장소에 커밋

## 19. 정리

본 문서는 SmartPark 프로젝트의 작업 기준을 정의하는 하네스 문서이다.

`PROJECT_RULES.md`는 단순한 규칙 목록이 아니라, SmartPark 프로젝트의 문서화, 코드 작성, AI 도구 활용, 형상관리, 품질 점검을 연결하는 기준 문서이다.

이 문서를 기준으로 이후 Claude Code는 React Native 프론트엔드 구현을, Codex는 Spring Boot 백엔드 설계와 API 문서화를 일관성 있게 수행할 수 있다.
