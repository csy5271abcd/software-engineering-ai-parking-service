# 1. 서론

## 1.1 문서 목적 및 범위
본 프로젝트 관리 계획서는 SmartPark의 AI 기반 주차난 해결 서비스에 대한 전반적인 내용을 체계적으로 정리하여, 프로젝트를 효율적으로 수행하기 위한 기준 문서로 활용하는 것을 목적으로 한다. 본 문서는 프로젝트 수행 과정에서 필요한 주요 관리 요소를 정의하고, 개발 진행 방향과 관리 방법을 일관성 있게 유지하는 데 목적이 있다.

본 문서는 다음과 같은 범위의 지표로 적용할 수 있다.

1. 프로젝트 개요 (프로젝트 정의, 주요 기능 정리)  
2. 개발 계획 및 환경 (개발 절차 모형, 내용 및 일정, 소프트웨어/하드웨어 환경)  
3. 팀 구성 (팀 구조/역할 및 책임)  
4. 품질관리 (팀 미팅, 변경 사항 및 산출물 관리)  
5. 산출물 (산출물 정의, 작성일 및 담당자)

즉, 본 계획서는 SmartPark 프로젝트의 전체적인 추진 방향을 정리하고, 개발 과정에서 발생할 수 있는 일정 관리, 역할 분담, 품질 관리, 형상 관리 등을 종합적으로 관리하기 위한 기준 문서이다.

## 1.2 프로젝트 개요

### 1.2.1 프로젝트 정의
AI 기반 주차난 해결 서비스 SmartPark는 도심 및 주거 지역에서 발생하는 주차 문제를 해결하기 위한 스마트 주차 서비스이다. 본 서비스는 사용자의 현재 위치와 목적지를 기반으로 주변 주차 가능 공간을 탐색하고, 곧 비워질 주차 공간 정보와 개인 소유 주차장의 공유 기능을 함께 제공하여 주차 공간 탐색의 효율성을 높이는 것을 목표로 한다.

또한 본 프로젝트는 React Native 기반 모바일 애플리케이션, Spring Boot 기반 백엔드, MySQL 데이터베이스, 그리고 Naver Maps API(Dynamic Map, GeoCoding, Reverse GeoCoding, Directions5 등)를 활용하여 구현한다. 지도 기반 탐색, 주소 변환, 경로 안내와 같은 핵심 기능을 시스템에 통합하고, AI 기반 혼잡도 분석을 통해 사용자가 실제로 주차 성공 가능성이 높은 공간을 선택할 수 있도록 지원한다.

아울러 본 프로젝트의 구현 과정에서는 Claude Code와 Codex를 활용한 바이브 코딩 방식을 반영하여, 기능 설계와 구현, 수정 과정을 보다 빠르고 유연하게 진행하고자 한다.

### 1.2.2 주요 기능 설명

| ID | 주요 기능 | 설명 |
|---|---|---|
| F01 | 현재 위치 기반 주차 공간 조회 | 사용자의 현재 위치를 기준으로 주변 주차 가능 공간을 지도에 표시하고, 거리·요금·운영시간·이용 가능 여부를 제공한다. |
| F02 | 곧 비워질 주차 공간 확인 | 이용자의 출차 예정 시간을 바탕으로 곧 이용 가능한 주차 공간 정보를 제공한다. |
| F03 | 주차장 공급자 등록 | 개인 소유자가 자신의 주차 공간 정보를 등록하고, 유휴 시간대에 공유할 수 있도록 지원한다. |
| F04 | NFC 기반 간편 결제 | NFC를 통해 주차 이용 시작·종료 및 요금 결제를 간편하게 처리한다. |
| F05 | AI 기반 혼잡도 분석 | 도착 예정 시간, 목적지, 과거 데이터 등을 바탕으로 주차장 혼잡도를 예측하고 추천한다. |

## 1.3 프로젝트 목표
본 프로젝트의 목표는 도심 및 주거 지역에서 발생하는 주차난 문제를 해결할 수 있는 AI 기반 주차 서비스 SmartPark를 개발하는 것이다. 사용자의 현재 위치와 목적지를 기반으로 주변 주차 가능 공간을 효율적으로 탐색할 수 있도록 지원하고, 곧 비워질 주차 공간 정보, 개인 주차장 공유 기능, NFC 기반 간편 결제 기능, AI 기반 혼잡도 분석 기능을 제공하여 주차 탐색 시간과 불편을 줄이는 것을 목표로 한다. 또한 본 프로젝트는 React Native, Spring Boot, MySQL, Naver Maps API를 활용하여 실제 서비스 형태의 시스템을 구현하고, 사용자와 주차 공간 공급자를 연결하는 스마트 주차 플랫폼을 구축하는 것을 목적으로 한다.

## 1.4 용어 정의
본 문서의 이해를 돕기 위해 사용된 모든 용어 및 약어를 설명하고 정의한다.

| 용어 | 설명 |
|---|---|
| API | 응용 프로그램 간 기능이나 데이터를 주고받을 수 있도록 제공되는 인터페이스 |
| React Native | 하나의 코드베이스로 모바일 애플리케이션을 개발할 수 있는 프레임워크 |
| Naver Maps API | 지도 표시, 주소 변환, 경로 탐색 등 위치 기반 기능을 제공하는 네이버 지도 API |

| AI 혼잡도 분석 | 시간대, 위치, 과거 이용 데이터 등을 바탕으로 주차장 혼잡도를 예측하는 기능 |
| 바이브 코딩 | Claude Code, Codex 등 AI 도구를 활용하여 설계·구현·수정을 빠르게 진행하는 개발 방식 |

# 2. 개발 계획

## 2.1 개발 절차 모형
1) **소프트웨어를 개발하기 위한 개발 절차 모형**  
본 프로젝트는 지도 API 연동, 주차 공간 데이터 처리, AI 혼잡도 분석 등 다양한 기능이 포함되어 있어 개발 과정에서 요구사항의 수정과 보완이 발생할 가능성이 높다. 따라서 변화에 유연하게 대응하고, 기능을 짧은 주기로 개발·점검할 수 있도록 Agile 방법론의 Scrum 모델을 적용한다. 또한 구현 과정에서는 Claude Code와 Codex를 활용한 바이브 코딩 방식을 반영하여 개발 효율을 높이고자 한다.

2) **분석, 설계를 진행하기 위한 방법론**  
본 프로젝트는 모바일 앱, 백엔드 서버, 데이터베이스, 외부 지도 API가 연계된 구조이므로, 각 기능을 명확하게 구분하고 확장 가능하도록 설계할 필요가 있다. 이를 위해 객체지향 방법론을 기반으로 분석과 설계를 진행하며, React Native 프론트엔드, Spring Boot 백엔드, MySQL 데이터베이스, Naver Maps API 연동 구조를 중심으로 시스템을 구성한다.

# 3. 팀 구성

# 4. 품질 관리

## 4.1 팀 미팅 계획
1) **Sprint Planning Meeting**  
- 팀 미팅 시간 : 매주 목요일 7시  
- 토의 내용 : Sprint 목표와 Sprint Backlog를 계획  
- 미팅 참석자 : 팀원, 팀장

2) **Daily Scrum Meeting**  
- 팀 미팅 시간 : 매일 오후 6시에 30분간 진행  
- 토의 내용 : 어제 한 일, 오늘 할 일, 장애 현상 등을 공유  
- 미팅 참석자 : 팀원, 팀장

3) **Sprint Review**  
- 팀 미팅 시간 : Sprint 종료 시점  
- 토의 내용 : Sprint 기간 동안 팀원 전체가 각자 한 일 리뷰  
- 미팅 참석자 : 팀원, 팀장

4) **Sprint Retrospective**  
- 팀 미팅 시간 : Sprint 종료 시점  
- 토의 내용 : Sprint 기간 동안 팀 내부에서 발생한 일들을 회고하며 개선할 것, 잘한 것, 새로 시작할 것을 도출

5) **비정기 회의**  
- 프로젝트 진행에 문제가 발생하여 회의가 필요한 경우에 진행된다.  
- 비정기 회의는 팀장 또는 지도교수 또는 멘토에 의해 요청될 수 있다.  
- 미팅 참석자 : 팀원, 팀장, (지도교수, 멘토)

## 4.2 변경 사항 관리 방법
- 기능 변경을 위해 팀원 전체가 권한을 가져야 하며 다수결의 합의가 필요하다.  
- 변경사항이 발생되는 경우 전후에 대해 반드시 기록물로 남긴다.  
- 관련 산출물은 팀원이 전부 소지한다.  
- 기능 변경을 위해서는 팀원 전체의 합의가 필요하지만, 의견 충돌로 진행이 멈출 시에는 팀장이 좀 더 강력한 발언권을 갖는다.  
- 변경 사항이 결정되면 지도 교수님께 반드시 보고하고 경우에 따라 또 다시 변경될 수 있다.

## 4.3 산출물 관리 방법
### (1) 산출물 식별 및 명명 방법
본 프로젝트의 산출물은 요구사항, 설계, 일정, 테스트, 소스코드로 구분하여 관리한다. 각 산출물은 Git 저장소 내 정해진 디렉터리에 저장하며, 파일명과 버전 정보를 통해 식별 가능하도록 관리한다.

- 요구사항 관련 산출물  
  - 프로젝트정의서 : `/docs/requirements`  
  - 요구사항정의서 : `/docs/requirements`  
  - 요구사항분석서 : `/docs/requirements`

- 설계 관련 산출물  
  - 소프트웨어설계서 : `/docs/design`

- 일정 관련 산출물  
  - 프로젝트관리계획서 : `/docs/plan`

- 테스트 관련 산출물  
  - 인스팩션예제 : `/docs/test`  
  - 테스트결과서 : `/docs/test`

- 소스코드  
  - 소스코드 : `/src`

또한 산출물의 버전은 `v주.부.수` 형식으로 관리한다.  
예를 들어 `v1.0.0`은 최초 확정 버전, `v1.1.0`은 기능 추가, `v1.1.1`은 오타 및 경미한 수정 사항을 의미한다.

- Major : 요구사항 변경  
- Minor : 기능 추가  
- Patch : 오타 및 경미한 수정

### (2) 산출물의 버전 관리 방법 및 변경 기록 방법
본 프로젝트의 모든 산출물은 Git을 이용하여 형상관리하며, 모든 변경 사항은 commit 메시지와 변경 이력을 통해 기록한다.

변경이 필요한 경우에는 변경 필요성을 확인한 뒤, 변경요청서(CR 문서)를 작성하고 별도의 브랜치에서 수정 작업을 수행한 후 main 브랜치에 병합한다.

브랜치 전략은 다음과 같다.

- `main` : 최종본 유지  
- `draft` : 작업 중 문서 관리  
- `review` : 검토 단계 문서 관리  
- `experiment` : 실험용 설계안 및 임시 작업 관리

또한 commit 메시지는 아래 형식으로 통일하여 기록한다.

- 형식 : `[구분자-번호] 변경 내용`  
- 예시 : `[CR-01] 요구사항 3번 수정 - 로그인 정책 변경`

구분자는 다음과 같이 사용한다.

- `[CR]` : 변경 요청  
- `[FEAT]` : 새 기능 추가  
- `[FIX]` : 오류 수정  
- `[DOCS]` : 문서 수정

변경 이력 관리를 위해 `git log`, `git tag`, `CHANGELOG.md`를 함께 사용하며, 주요 개발 단계에서는 다음과 같은 태그를 부여한다.

- `requirements_freeze` : 요구사항 확정  
- `design_complete` : 설계 완료  
- `beta_release` : 시제품 완료  
- `final_release` : 최종 제출

산출물의 버전 관리와 변경 기록은 본 프로젝트 수행자인 최수연이 직접 담당한다.

### (3) 산출물의 저장 및 백업 방법
본 프로젝트의 모든 산출물은 GitHub 원격 저장소에 등록하여 관리한다. 문서 산출물과 소스코드는 모두 Git 저장소에 포함시키며, 로컬 저장소와 원격 저장소에 이중으로 보관한다.

- 저장소 관리 방법 : GitHub 원격 저장소 사용  
- 저장 대상 : 문서 산출물, 테스트 결과, 소스코드 전체  
- 백업 방법 : 로컬 저장 + 원격 저장소 이중 보관  
- 동기화 주기 : 최소 주 1회 이상 push 수행

이와 같은 방법을 통해 산출물의 유실을 방지하고, 변경 이력을 체계적으로 추적할 수 있도록 한다.
